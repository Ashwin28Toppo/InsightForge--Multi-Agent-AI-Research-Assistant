# InsightForge — Frontend-Focused API Reference

**For Antigravity (Phase 2E frontend agent).** The single source of truth for
how the frontend talks to the backend. Base URL (dev):
`http://127.0.0.1:8000` — CORS already allows `http://localhost:3000` and
`http://127.0.0.1:3000`.

Every response carries an **`X-Request-ID`** header (a UUID generated by the
server, or your value echoed back if you send one).

Recommended frontend structure:

```
frontend/lib/
  api/
    client.ts          # fetch wrapper: base URL, JSON, X-Request-ID, errors
    research.ts        # submitResearch, getJobStatus, getJobProgress
    health.ts          # getHealth
  sse/
    research-stream.ts # subscribeResearchStream(jobId, handlers)
  types/
    api.ts             # all API types below
```

---

## General conventions

- **Content-Type**: `application/json` for request bodies.
- **Errors**: non-2xx responses return a JSON body with a `detail` field.
- `404` → `{"detail": "job not found"}` (unknown **or TTL-expired** job).
- `422` → `{"detail": [{type, loc, msg, ...}]}` (invalid body).
- `500` → `{"detail": "Internal server error"}` (never internal details).
- Jobs are **in-memory** — lost on backend restart; expired after
  `JOB_TTL_SECONDS` (default 3600 s).

## 1. GET /health

| Field | Value |
|---|---|
| Method / URL | `GET /health` |
| Response 200 | `{"status": "ok"}` |
| Purpose | Liveness probe; backend reachability chip |

**Frontend usage**: on app load / retry buttons, show a "Backend online /
offline" indicator. Non-200 → backend unreachable.

**Loading state**: a small pending state on the chip while checking.

**Error handling**: any network error or non-200 → "offline" state; retry
button re-checks. Never blocks the rest of the UI.

## 2. POST /research

**Starts a research job.** Returns immediately; the pipeline runs in the
background.

**Request**

```json
{
  "query": "string"        // required, non-blank (whitespace stripped)
}
```

**Responses**

| Status | Body |
|---|---|
| `202` | `{"job_id": "uuid", "status": "queued"}` |
| `422` | validation error (`detail` list) — missing/blank/whitespace `query` |
| `500` | `{"detail": "Internal server error"}` |

**Statuses on the created job**: `queued` → `running` → `completed | failed`.

**Frontend usage**
1. `POST /research {"query": q}`.
2. On 202 → navigate to `/research/{job_id}` and subscribe to SSE.
3. Disable the submit action while a job is in flight — **each call creates a
   distinct job** (no idempotency key). Guard against duplicate submissions.

**Loading state**: `SUBMITTING` — disable button, spinner, "Submitting…".

**Error handling**
- 422 → inline field error under the query input ("Query can't be empty").
- Network → inline error + allow retry (same query).
- 500 → generic error, allow retry.

## 3. GET /research/{job_id}

**Current job status + final result.**

**Responses**

| Status | Body |
|---|---|
| `200` | `{ "job_id": "...", "status": "queued" \| "running" \| "completed" \| "failed", "result"?: {...}, "error"?: "string" }` |
| `404` | `{"detail": "job not found"}` (unknown or TTL-expired) |
| `500` | `{"detail": "Internal server error"}` |

**Body shape notes** (keys appear/disappear by state):
- `queued` / `running` → only `job_id` + `status`.
- `completed` → `result` present (opaque object — see below).
- `failed` → `error` present (safe string like `"RuntimeError: ..."`).

**`result` object** (best-effort — treat every field as optional; the shape
comes from the pipeline):

```ts
interface ResearchResult {
  query?: string;
  report?: string;            // final markdown report (render with a markdown renderer)
  report_draft?: string;      // internal alias — usually same as report
  search_results?: string;    // raw search summary text
  sources?: string[];         // source URLs
  citations?: Citation[];     // numbered citations
  evidence?: Evidence[];      // evidence items (E1, E2, ...)
  claims?: string[];          // extracted claims
  fact_checks?: FactCheck[];  // claim verdicts
  confidence?: string;        // "high" | "medium" | "low" (or unknown)
  critic_feedback?: string;   // optional critic note
  critic_score?: number | null;
  errors?: string[];          // safe non-fatal errors
}

interface Citation {
  index?: number;             // [1], [2], ...
  source_type?: "web" | "rag";
  title?: string;
  url?: string | null;
  document_id?: string | null;
  page?: number | null;
  chunk_index?: number | null;
}

interface Evidence {
  id?: string;                // "E1", "E2", ...
  source_type?: "web" | "rag";
  text?: string;              // truncated snippet
  title?: string;
  url?: string | null;
  document_id?: string | null;
  page?: number | null;
  chunk_index?: number | null;
  score?: number;
}

interface FactCheck {
  claim?: string;
  verdict?: string;           // "supported" | "unsupported" | "needs more research" | ...
  confidence?: number;
  evidence_refs?: string[];   // e.g. ["E1"]
}
```

**Frontend usage**
- Poll while `running` (backup to SSE) or on `completed` fetch the result.
- After an SSE `completed` event, call this to get the full report.
- Render `report` (markdown), `sources`, `citations`, `evidence`,
  `fact_checks`, `confidence`.

**Loading state**: skeleton while fetching.

**Error handling**: 404 → "Research not found or expired" state (offer new
research); network → retry; `result.errors` non-empty → warning banner.

## 4. GET /research/{job_id}/progress

**Live progress snapshot (polling).**

**Response 200**

```json
{
  "job_id": "uuid",
  "status": "queued" | "running" | "completed" | "failed",
  "current_step": "string | null",   // most recent completed stage, or null
  "completed_steps": ["plan", "research", "evidence", "..."]  // ordered
}
```

**Statuses / errors**: `404` unknown/expired, `500` internal.

**Frontend usage**
- Fallback/poll when SSE is unavailable or while reconnecting.
- `current_step` = latest stage; `completed_steps` = ordered history.
- **Do not assume a fixed number of steps.** Stages may repeat if the
  research loop is enabled (default is a single pass of 9 stages:
  plan, research, evidence, claim_extraction, fact_check, citation,
  confidence, writer, critic — but treat the list as open-ended).

**Loading state**: skeleton timeline on first poll.

**Error handling**: 404 → job gone; network → retry; failed status → read
`error` from the status endpoint.

## 5. GET /research/{job_id}/stream — SSE

**Live progress via Server-Sent Events.** Media type `text/event-stream`.

### Response headers (important)

- `Content-Type: text/event-stream`
- `Cache-Control: no-cache`
- `X-Accel-Buffering: no`
- `X-Request-ID: <uuid>`
- CORS headers present (`Access-Control-Allow-Origin`, credentials, expose
  `X-Request-ID`).

### Event format

Each event is:

```
event: <name>
data: <json>

```

### Event contract

| Event | When | `data` payload |
|---|---|---|
| `queued` | job created, worker not started | progress payload, `status: "queued"` |
| `progress` | job running, a stage completed | progress payload, `status: "running"` |
| `completed` | **terminal** — job finished | progress payload, `status: "completed"` |
| `failed` | **terminal** — job errored | progress payload + `error` (safe string) |

**Progress payload** (all four events):

```json
{
  "job_id": "uuid",
  "status": "queued" | "running" | "completed" | "failed",
  "current_step": "string | null",
  "completed_steps": ["plan", "research", "..."]
}
```

The `failed` event additionally includes:

```json
{ "error": "RuntimeError: <safe message>" }
```

### Rules the frontend MUST follow

1. **`completed` / `failed` are terminal.** The stream closes immediately
   after. Do not wait for more events.
2. **SSE does NOT contain the final report.** After `completed`, call
   `GET /research/{job_id}` to fetch `result`.
3. **State-snapshot replay.** On (re)connect the server replays the current
   state — the **first event may be `progress` or `completed`**, not
   necessarily `queued`. Treat every event as a full state snapshot, not a
   delta.
4. **Reconnection is safe and required.** If the connection drops:
   - Do **NOT** POST a new research job.
   - Reconnect to the same `GET /research/{job_id}/stream` URL.
   - While reconnecting, optionally poll `GET /research/{job_id}/progress`
     to avoid gaps.
5. **No fixed step count.** `completed_steps` is an ordered, open-ended list.

### Frontend usage (isolated SSE module)

```ts
// lib/sse/research-stream.ts
subscribeResearchStream(jobId, {
  onQueued(payload), onProgress(payload),
  onCompleted(payload), onFailed(payload, error),
  onReconnect(), // optional
});
```

- Native `EventSource` works (GET, no custom headers needed — the server
  generates an `X-Request-ID`). It auto-reconnects, but you should still
  implement your own reconnect with backoff for full control.
- Guard against **duplicate handlers** on React StrictMode double-mount.

## Suggested TypeScript types (put in `lib/types/api.ts`)

```ts
export type JobStatus = "queued" | "running" | "completed" | "failed";

export interface ResearchJobResponse {
  job_id: string;
  status: "queued";
}

export interface ResearchStatusResponse {
  job_id: string;
  status: JobStatus;
  result?: ResearchResult;
  error?: string;
}

export interface ResearchProgressResponse {
  job_id: string;
  status: JobStatus;
  current_step: string | null;
  completed_steps: string[];
}

export interface SseProgressPayload {
  job_id: string;
  status: JobStatus;
  current_step: string | null;
  completed_steps: string[];
  error?: string;
}
```

## API layer contract (frontend)

Keep all networking in `lib/api/*` and `lib/sse/*`:

- `lib/api/client.ts` — base URL from `NEXT_PUBLIC_API_BASE_URL` (default
  `http://127.0.0.1:8000`), JSON handling, typed error parsing, optional
  `X-Request-ID` passthrough.
- `lib/api/research.ts` — `submitResearch(query)`,
  `getJobStatus(jobId)`, `getJobProgress(jobId)`.
- `lib/api/health.ts` — `getHealth()`.
- `lib/sse/research-stream.ts` — `subscribeResearchStream(jobId, handlers)`
  with reconnect + cleanup.
- **No component ever calls `fetch()` directly.**
